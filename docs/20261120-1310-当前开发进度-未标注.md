## 阻塞问题一：pandas 2.0.3 无 cp312 wheel

`pandas==2.0.3` 在 PyPI 上没有 cp312 wheel（已核实），Ubuntu 24.04 的 Python 3.12 会退化为源码编译，缺少编译环境必然失败。

改用 `pandas==2.2.3`（已核实存在 `cp312-cp312-manylinux_2_17_x86_64` wheel）。

## 阻塞问题二：内核 7.0 无法运行 picosnitch 1.0.3

现象：`picosnitch.service` 状态 `activating`，日志刷满 BPF 编译错误，`NRestarts` 持续增长。

根因：picosnitch 1.0.3 在运行时用系统 BCC 编译 BPF 源码。Ubuntu 24.04 只有 BCC 0.29.1，其内置的内核兼容头不认识 7.0 内核的新常量：

```
error: use of undeclared identifier 'BPF_LOAD_ACQ'
error: use of undeclared identifier 'BPF_STORE_REL'
error: use of undeclared identifier 'BPF_F_CPU'
error: use of undeclared identifier 'BPF_F_ALL_CPUS'
error: use of undeclared identifier 'BPF_TRACE_FSESSION'
```

这些常量定义在内核 uapi 头里（如 `uapi/linux/bpf.h:1396` 的匿名 enum），但 `linux/bpf.h` 内部引用时没有引入，导致 BCC 的 C 编译环境里不可见。实测补宏无效（缺的不只两三个），BCC 需升级到 0.37+（其 changelog 写明 "Support for kernel up to 7.1"），而 Ubuntu 24.04 仓库只有 0.29.1。

解决方案：升级到 picosnitch 2.2.1。2.x 改为**预编译 CO-RE BPF 对象**（`picosnitch/bpf/picosnitch.bpf.o`），运行时不需要编译，天然不受 BCC 版本影响。已在 uw 上实测：服务 active、`NRestarts=0`、采集到 100+ 条连接记录。

## 2.x 带来的破坏性变化（已全部适配）

| 项 | 1.x | 2.x |
|---|---|---|
| 代码形态 | 单文件 `site-packages/picosnitch.py` | 包目录 `site-packages/picosnitch/` |
| 启动守护进程 | `picosnitch start-no-daemon` | 同左（保留） |
| 启动 Web | `picosnitch start-dash` | `picosnitch webui` |
| Web 监听地址 | 环境变量 `HOST` / `PORT` | 环境变量 `PICOSNITCH_HOST` / `PICOSNITCH_PORT` |
| 配置 | 无独立配置文件 | `/etc/picosnitch/config.toml` |
| 数据库 | `/root/.config/picosnitch/snitch.db` | `/var/lib/picosnitch/picosnitch.db` |
| 连接表结构 | `connections.exe` 直接存路径 | `connections.exe_id` → JOIN `executables.exe` |
| 系统依赖 | 需要 `bpfcc-tools` | 不需要 BCC |
| systemd 关键项 | 无 | `LimitMEMLOCK=infinity`（libbpf 需 mmap 约 16 MiB 环形缓冲区） |

因此删除了原有的 `patch_picosnitch_ui`（对 2.x 完全不适用），新增 `configure_picosnitch` 写 config.toml（关闭桌面通知与 GeoIP 下载）。

## 阻塞问题三：dpkg 锁导致的部署中断（首次部署时才暴露）

`unattended-upgrades` 持有 dpkg 锁，安装脚本第一次 apt 就失败。

第一次修复用 `pgrep -f "unattended-upgr"` 判断，结果误判：`unattended-upgrade-shutdown --wait-for-signal` 是**常驻守护进程**，一直存在但并不持锁，导致脚本空等 600 秒后超时。

最终方案：直接调用 apt，只在报错文本包含 `Could not get lock` / `Unable to acquire the dpkg frontend lock` 时等 10 秒重试，最多 10 分钟。

## 已知无害告警

`/var/log/picosnitch/error.log` 有一条：

```
BPF.attach_trace() skipped for tcp_read_sock: io_zcrx_recv_skb address unavailable
```

含义：内核未暴露 `io_zcrx_recv_skb` 符号，io_uring 零拷贝接收的字节不会被统计。普通 TCP 收发不受影响。若将来用到 io_uring 零拷贝应用，这部分流量会漏计。
