## 优先级高

### 1. 关机流程真实验证

目前只验证到"预警邮件能发"。`ACTION=poweroff` 分支的实际关机行为尚未在真机测试（关机后服务器会下线，需谨慎安排时机）。

建议：选一台非关键机器，临时把 `LIMIT_BYTES` 调到一个略高于当前值的数，观察是否按预期发信 + 关机 + 重启后累计是否保留。

### 2. io_uring 零拷贝流量漏计

内核 7.0-azure 未暴露 `io_zcrx_recv_skb`，picosnitch 无法统计 io_uring 零拷贝接收的字节。

```
BPF.attach_trace() skipped for tcp_read_sock: io_zcrx_recv_skb address unavailable
```

普通 TCP 不受影响。若 uw/ue 上跑的程序用 io_uring（新版 nginx、部分数据库），统计会有缺口。建议用 nftables 计数做交叉校验。

## 优先级中

### 3. Bark 推送作为邮件兜底

邮件可能被忽略或进垃圾箱。用户已有 Bark：`https://api.day.app/<BARK_DEVICE_KEY>`。

建议增加 `ENABLE_BARK=1` + `BARK_URL`，关机前同时推送。一行摘要即可，无需附件。

### 4. Web 端编辑预警线与动作

现在只能改阈值，`WARN_PERCENT` 和 `ACTION` 需手动改 `/etc/default/traffic-guard`。

### 5. 状态文件手动重置入口

误判或调整计费周期后只能登服务器删文件。建议 Web 端加"重置本周期统计"按钮。

### 6. 部署回滚

`git pull --ff-only` 后直接重装，新版本失败会停在半新半旧状态。建议部署前记录 commit，失败时自动回退。

### 7. 部署脚本禁止删除数据目录

我在调试时用临时脚本删过 `/var/lib/picosnitch`，清空了已采集数据。正式安装脚本没有这个行为，但应在文档和脚本注释中明确禁止。
