# LinuxNet 安全与运维说明

## Web 服务边界

Picosnitch Dash 和 Traffic Guard Web 默认只监听回环地址。公网访问应通过 SSH 隧道，或由提供 TLS、认证和限流的反向代理转发，禁止直接把 `5100`、`5101` 端口开放到公网。

Traffic Guard Web 即使只监听本机，也强制使用 Basic Auth。用户名固定为 `admin`，随机密码保存在 `/etc/traffic-guard/web-token`，权限为 `0600`。修改阈值的请求还必须携带基于该密码生成的 CSRF 令牌。

该 Web 服务具有修改 `/etc/default/traffic-guard` 和启动检查服务的权限。检查服务可能执行关机，因此认证文件、反向代理配置和 SSH 访问权限都应按 root 级敏感度管理。

邮件配置文件 `/etc/traffic-guard/gmail-notify.conf` 保存 SMTP 明文密码，权限 `0600`。写入时所有值用单引号包裹，避免密码中的 `#`、`(`、`!` 等字符被 shell 解析。

## 凭据泄露：先轮换，再处理历史

仓库中的占位符不是有效配置。已出现在历史中的 189 邮箱口令和 Bark（推送服务）设备密钥应视为失陷；删掉当前文档并不会撤销它们。

1. 由账号所有者在 189 邮箱更换已泄露的登录密码或撤销原授权码，优先为发信单独签发授权码；检查活动会话、发信记录及复用密码的服务。重新签发 Bark 设备密钥并使旧地址失效，检查通知记录。
2. 在受控终端更新所有发信节点和通知客户端，保持配置权限 `0600`；分别验证新凭据有效、旧凭据无效。工单、聊天、提交说明及日志不要粘贴任一凭据。
3. 如需清理历史，先取得维护者明确批准，冻结写入并受限备份；在隔离的镜像克隆中用 `git filter-repo` 分别替换文件内容和提交说明，核查所有分支、标签及提交说明。经团队确认再协调更新远端引用，通知协作者重新克隆；另行处理拉取请求缓存、分叉、构建产物、日志和备份。不要将含原值的替换清单写入仓库。历史清理不能代替轮换。本次没有执行轮换或历史重写。

### 阻止再次提交

在仓库根目录运行 `git config --local core.hooksPath .githooks` 启用本地钩子；已有自定义钩子路径时先整合，不要覆盖。提交前检查暂存新增行，提交时另查标题和正文。也可用 `python3 scripts/check_secrets.py --range BASE HEAD` 离线检查两个提交之间每一笔新增提交。持续集成在推送及拉取请求上执行范围检查；新分支以默认分支为排除基线。只报告类别，不输出原文；未能解析基线时检查失败，不静默放行。规则仅覆盖已知模式，不替代凭据管理和人工检查。

## 防护措施

- 请求体上限为 16 KiB。
- 每个连接读取超时为 5 秒。
- 同时处理的请求线程最多 32 个。
- 配置通过同目录临时文件和原子替换写入，并保留管理员手工添加的其它键。
- 阈值限制在 Bash 64 位有符号整数可表达的范围内。
- Web 修改后会检查 `systemctl start traffic-guard.service` 的退出状态，不再把失败显示为成功。

## 流量状态文件

`/var/lib/traffic-guard/<网卡>.baseline` 记录本周期累计出站流量与上次看到的内核计数器，权限 `0600`，由检查脚本原子写入。它决定何时关机，属于安全敏感文件：

- 删除它会清空本周期累计（从当前计数器重新起算），等同于手动重置配额。
- 篡改它可让守卫永不触发。该目录只应对 root 可写。
- 状态文件同时记录 `WARNED`/`ALERTED`，用于保证同一事件只发一封邮件。
- `SHUTDOWN_DONE` 记录本周期已自动关机的次数，用于“关机一次后不再关机”。删掉状态文件或通过 Web 复位都会把它清零，等于重新开放自动关机；这是有意的设计，复位需要认证。
- **复位只清 `ALERTED`/`SHUTDOWN_DONE`，不清 `TOTAL_BYTES`**：否则“复位”就变成了绕过配额的免费重置。要真正清零累计，只能删状态文件（等价于手动重置配额）。

## 安装与验证

安装脚本固定 Picosnitch 版本。每次部署先用 `--force-reinstall` 重装上游包，保证安装脚本可以重复执行且不会残留改过的文件。

Picosnitch 2.x 不再需要运行时编译 BPF，也不再需要 `bpfcc-tools`。安装脚本会在部署结束后等待数据库产生连接记录，只有真正采集到数据才算成功，避免服务处于 `activating` 却误判为可用。

安装结束必须满足以下条件：

- 四个 systemd 单元均为 active。
- Picosnitch Web 返回 HTTP 200。
- Traffic Guard Web 经认证后返回 HTTP 200。
- `/var/lib/picosnitch/picosnitch.db` 中出现匹配本次回环探测的新连接记录。安装脚本先记录最大行号，再建立探测连接；已有记录或无关连接不算通过。

若验证失败，先查看：

```bash
journalctl -u picosnitch.service -u picosnitch-dash.service -u traffic-guard.timer -u traffic-guard-web.service --no-pager -n 200
```

## GitHub Actions 部署

只有启用 `ENABLE_DEPLOY=true` 且本仓库 `main` 分支的推送通过 CI（持续集成）时才部署。服务器地址来自 `DEPLOY_SERVER_HOSTS`，支持逗号、空格或换行分隔的多台机器（旧名 `DEPLOY_SERVER_HOST` 仍可用）；逐台按顺序部署，任一失败即中止，已成功的机器保持新版本。目标路径固定为 `/opt/linuxnet`；目录不存在时克隆，已有目录须为来源正确、位于 `main` 的独立干净仓库。符号链接、本地改动、未跟踪的非忽略文件、不能快进的本地提交都会中止部署；`__pycache__`、`.DS_Store` 等被忽略的产物不影响。拉取后核对远端 `main` 与通过检查的提交标识（SHA），快进后再次核对本地版本，再执行安装；若分支已前进，旧任务停止。安装以 `sudo -n` 执行，执行前校验部署用户具备免密 sudo（云镜像通常禁用 root 直接登录）。服务器主机密钥须预先核验并存入 `DEPLOY_KNOWN_HOSTS`，不在运行时临时信任新密钥。

部署密钥应为专用密钥，不与个人登录密钥复用；吊销时从各服务器 `authorized_keys` 删除对应公钥即可。
