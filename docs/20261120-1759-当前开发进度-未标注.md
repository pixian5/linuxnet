## 升级路径

```
24.04 LTS
  → (full-upgrade + 重启)
  → do-release-upgrade            → 26.04.1 LTS
  → (改 Prompt=normal + 重启)
  → do-release-upgrade -d         → 26.10
  → (重启加载新内核)
```

Ubuntu 不允许跨版本直升，26.10 是非 LTS，必须加 `-d` 参数，且 `Prompt` 要从 `lts` 改成 `normal`。

## 过程中遇到的五个问题

### 1. 升级前必须先装完所有更新

`do-release-upgrade` 直接报：

```
Please install all available updates for your release before upgrading.
```

必须先 `apt-get full-upgrade`。

### 2. 10 个 systemd 包被“分阶段发布”卡住

`full-upgrade` 后仍有 10 个包未升级（`libsystemd0`、`systemd`、`udev` 等），原因是 Ubuntu 的 Phased Update 机制。显式安装即可：

```bash
apt-get -y install systemd libsystemd0
```

### 3. 每次升级前都需要重启

两次都遇到：

```
You have not rebooted after updating a package which requires a reboot.
Please reboot before upgrading.
```

内核更新后必须重启，`do-release-upgrade` 才会放行。整个升级过程共重启 3 次（24.04→26.04 前 1 次、26.04→26.10 前 1 次、每次升级完成后各 1 次）。

### 4. Python 大版本升级导致 venv 失效（关键）

24.04 是 Python 3.12，26.04/26.10 是 **3.14**。升级后 `picosnitch` 服务无限重启：

```
/opt/picosnitch-venv/bin/python3: No module named picosnitch
picosnitch.service: Scheduled restart job, restart counter is at 19.
```

原因：venv 目录还叫 `lib/python3.12`，但解释器已经是 3.14，`pyvenv.cfg` 里记录 `version = 3.12.3`。

**修复**（已并入安装脚本 v0.0.13）：检测 `pyvenv.cfg` 的 `version` 与当前 `python3` 是否一致，不一致就删掉重建。

```
[linuxnet] 检测到 Python 版本变化（venv 3.14.4 -> 系统 3.14.8），重建 venv
```

已在 ue 上验证自动重建生效。

### 5. sudo 在升级过程中会短暂消失

升级替换 `sudo` 包期间，`/usr/bin/sudo` 不存在，SSH 执行 `sudo` 报 `command not found`。这是正常现象，等升级走完即可；但如果此时需要紧急操作就会很被动。

**教训**：升级期间不要依赖 `sudo`，读日志用普通用户可读路径（日志文件由 `chown x:x` 处理过）。

### 6. ue 首次升 26.10 被拒

```
Upgrades to the development release are only available from the latest supported release.
```

但 `do-release-upgrade -c -d` 又显示可用。重试一次即成功，判定可能与 apt 缓存状态有关。

## 自动化手段

- 用 `tmux` 包裹整个升级，避免 SSH 断连中断
- `DEBIAN_FRONTEND=noninteractive` + `DistUpgradeViewNonInteractive` 实现无人值守
- dpkg 冲突项用 `--force-confold --force-confdef` 保留现场配置
- 日志写入 `/var/log/upgrade-<时间戳>.log`，末尾打 `EXIT_CODE=<code>` 便于判断结果
