## 优先级高

### 1. 关机流程真机验证

阈值、预警、邮件都已验证，但 `ACTION=poweroff` 的实际关机与重启后累计是否保留，尚未在真机测试（关机后服务器会下线）。

建议：选一台非关键机器，临时把 `LIMIT_BYTES` 调到略高于当前累计值，观察：
1. 是否发关机邮件
2. 是否真的执行 `poweroff`
3. 重启后 `TOTAL_BYTES` 是否保留（这是 v0.0.3 修复的核心逻辑）

### 2. 邮件发送失败没有告警

`send-shutdown-mail.sh` 用 `|| true` 吞掉了所有失败。若 189 邮箱改密码或限流，关机通知会静默丢失，而服务器照常关机。

建议：发信失败时写一条 `logger` 严重级别日志，便于事后用 `journalctl -t traffic-guard` 发现。

## 优先级中

### 3. 50 GB 配额的计量口径可能不一致

云厂商的“50 GB/月”通常统计**出站公网流量**，而本项目的 `tx_bytes` 是**网卡全部出站字节**，包含：

- 内网通信（VPC 内部、与 Azure 元数据服务）
- TCP 重传、协议开销
- IPv6 流量

实测 uw 一小时产生 54 MiB、ue 593 MiB，若按这个速率推算，ue 月累计会远超 50 GB。**建议核对云控制台的实际计费数字与本地统计的比值**，必要时把阈值调低到厂商配额的 80% 左右，留出计量差异缓冲。

### 4. Bark 推送作为邮件兜底

邮件可能进垃圾箱或被限流。用户已有 Bark：`https://api.day.app/<BARK_DEVICE_KEY>`。建议增加 `ENABLE_BARK=1`。

在 189 存在限流的前提下，这条比之前更有必要。

### 5. Web 端编辑预警线与动作

现在只能改阈值，`WARN_PERCENT`、`ACTION` 需手动改 `/etc/default/traffic-guard`。

### 6. 状态文件手动重置入口

误判或调整计费周期后只能登服务器删文件。

### 7. 部署回滚

`git pull --ff-only` 后直接重装，新版本失败会停在半新半旧状态。
