# 幂等部署经验

## 为什么“打补丁 + 版本固定”会互相打架

`pip install --upgrade 包==固定版本` 在版本已满足时**不会重装**，被改过的文件会一直留着。因此任何“安装后修改第三方源码”的脚本，第二次执行必然面对已打补丁的文件。

两种正确做法：

1. 强制还原：`pip install --upgrade --force-reinstall --no-deps 包==版本`，每次从零打补丁。
2. 幂等补丁：替换前同时统计“旧串”和“新串”出现次数。
   - 旧串命中期望次数 → 正常替换。
   - 旧串为 0 且新串已达期望次数 → 已打过补丁，跳过。
   - 其余 → 真正的不兼容，报错退出。

## 但更好的选择是不打补丁

本项目最终放弃了源码补丁：picosnitch 从 1.x 升到 2.x 后，单文件 `picosnitch.py` 变成了包目录，所有补丁字符串都不存在了，补丁逻辑直接报废。

**教训**：对第三方源码打补丁是脆弱的。优先用官方支持的配置项、环境变量、systemd 参数来定制；只有在完全没有扩展点时，才考虑打补丁，并同时做幂等 + 强制还原双重保险。

## dpkg 锁：不要用 pgrep 判断

云镜像的 `unattended-upgrades` 常会持锁导致 apt 失败。但 **不能**用 `pgrep -f "unattended-upgr"` 判断，因为 `unattended-upgrade-shutdown --wait-for-signal` 是常驻守护进程，一直存在却并不持锁，会造成误判空等（实测空等满 600 秒后超时）。

正确做法：直接调用 apt，只在输出包含 `Could not get lock` 或 `Unable to acquire the dpkg frontend lock` 时才 sleep 重试。

```bash
apt_with_lock_retry() {
  local waited=0 output
  while :; do
    if output=$(DEBIAN_FRONTEND=noninteractive apt-get "$@" 2>&1); then
      printf '%s\n' "$output"; return 0
    fi
    printf '%s\n' "$output" >&2
    if printf '%s' "$output" | grep -q "Could not get lock\|Unable to acquire the dpkg frontend lock"; then
      [ "$waited" -ge 600 ] && return 1
      sleep 10; waited=$((waited + 10)); continue
    fi
    return 1
  done
}
```

## 教训

- 安装脚本的“重复执行”必须显式测：对同一文件连续跑两次，而不是只跑一次看第一次通过。
- **不要在部署脚本里 `rm -rf` 数据目录**。我在调试时删过 `/var/lib/picosnitch`，把已采集的历史数据清空了。数据目录应只在明确要求重置时删除。

## 现场事实（uw / ue）

| 项 | 值 |
|---|---|
| 服务器 | `uw.sbbz.tech`（20.171.66.196）、`ue.sbbz.tech`（20.115.117.78） |
| 登录方式 | `x@<host>` + `~/.ssh/id_ed25519`，**root/ubuntu 均被拒**（云镜像禁用 root 直登） |
| sudo | `x` 用户免密 sudo 可用（`sudo -n true` 返回 0） |
| 部署路径 | `/opt/linuxnet` |
| 配额 | 50 GiB/月，阈值 `53687091200` |

本机 `~/.ssh/config` **没有** uw/ue 条目，直接 `ssh x@uw.sbbz.tech` 会失败，必须显式 `-i /Users/x/ed25519`。试过无效的组合：`root@`、`ubuntu@`、`azureuser@`、`~/.ssh/id_ed25519_ubuntu`、`~/.ssh/uk_sbbz_key`、`/Users/x/agent.pem`、`/Users/x/Downloads/aws.pem`。**不要因为默认 ssh 失败就断言服务器连不上。**

## GitHub Actions 多机部署

- 服务器列表用 `DEPLOY_SERVER_HOSTS`，逗号、空格、换行都能分隔：`mapfile -t hosts < <(printf '%s' "$targets" | tr ', ' '\n' | sed '/^$/d')`。
- **逐台串行**，不并行：任一台失败即中止，避免出现“一台新一台旧”还继续往下跑。
- GitHub Actions 里 `secrets.A || secrets.B` 不可靠，要在 shell 里做回退：`targets="${SERVER_HOSTS:-${SERVER_HOST_FALLBACK:-}}"`。
- 每台都执行完整校验（来源、分支、干净工作区、`FETCH_HEAD`、快进、`HEAD` 复核、免密 sudo），不因第一台成功就跳过第二台。

## 部署密钥

- 用 `ssh-keygen -t ed25519 -N '' -f /tmp/linuxnet_deploy` 生成**专用**密钥，不复用个人登录密钥。泄露时只影响部署，且能从 `authorized_keys` 精确删除。
- 追加公钥时去重：`grep -qF "$PUB" ~/.ssh/authorized_keys || echo "$PUB" >> ~/.ssh/authorized_keys`。
- 上传前先本地验证新密钥能登录且免密 sudo 可用，别等 CI 报错才发现。

## 主机密钥要先核验再用

`ssh-keyscan -t ed25519` 的结果必须与本机 `known_hosts` 已有条目**逐字节比对**，一致后才写入 `DEPLOY_KNOWN_HOSTS`。不要用 `StrictHostKeyChecking=no` 直接信任，那等于关掉中间人防护。

## 验证部署是否真的成功

不要只看 workflow 绿了就收工：

```bash
ssh -i /Users/x/ed25519 x@<host> 'cd /opt/linuxnet && git rev-parse HEAD && cat VERSION'
ssh -i /Users/x/ed25519 x@<host> 'sudo -n cat /etc/default/traffic-guard'              # 阈值必须仍是 50 GiB
ssh -i /Users/x/ed25519 x@<host> 'sudo -n cat /var/lib/traffic-guard/eth0.baseline'    # 累计不能归零
ssh -i /Users/x/ed25519 x@<host> 'systemctl is-active picosnitch picosnitch-dash traffic-guard.timer traffic-guard-web'
```

## 真机验证要隔离，别碰生产状态

验证守卫判定时，用 `STATE_FILE`、`MAIL_SCRIPT`、`POWEROFF_CMD` 指向 `/tmp` 下的临时文件，**不要用真实状态文件，也不要用真实 `poweroff`**：

```bash
TX_FILE=/sys/class/net/eth0/statistics/tx_bytes \
STATE_FILE=$W/state MAIL_SCRIPT=$W/fake-mail POWEROFF_CMD=$W/fake-poweroff \
LIMIT_BYTES=1000000 ACTION=poweroff WARN_PERCENT=80 \
bash /opt/linuxnet/templates/check-tx-shutdown.sh
```

**但要知道副作用**：这类验证会产生 `journalctl -t traffic-guard` 日志，看起来像真实事件。验证完要回读生产状态文件确认没被改。

## 坑：heredoc + 远程 bash 里的 `%` 转义

在 `ssh host '...'` 单引号串里写 `date +%%Y-%%m` 不会按预期展开，会得到字面的 `%Y-%m`，导致周期判断变成“新周期”而把累计清零。**先赋值 `P=$(date +%Y-%m)` 再引用 `${P}`**，不要在内联脚本里赌转义层级。

## 坑：测试数据写错会得出相反结论

验证“硬顶 150%”时用了累计 200%，本以为应走“不关机”分支，实际关机了——因为 200% 已超过硬顶。**验证前先算清百分比落在哪个区间**，否则会把正确行为误判成 bug。
