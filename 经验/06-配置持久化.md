# 配置持久化经验（部署类脚本必读）

## 核心原则

**安装脚本重跑时，不能覆盖运维在现场调过的配置。**

CI 部署、手动重装、版本升级都会重跑安装脚本。如果脚本用代码里的常量直接 `cat >` 配置文件，那么每一次重部署都会把现场调整清零。

本项目真实踩到：CI 部署把 `LIMIT_BYTES` 从 50 GB 重置回 1024 MiB，会导致服务器在两三天内误关机。

## 正确做法

环境变量 **未设置** 时，从服务器已有配置继承；显式设置时以环境变量为准。

```bash
read_existing() {
  local key="$1" file="/etc/default/traffic-guard"
  if [ -f "$file" ]; then
    sed -n "s/^${key}=//p" "$file" | tail -1
  fi
}

EXISTING_LIMIT="$(read_existing LIMIT_BYTES)"
if [[ "$EXISTING_LIMIT" =~ ^[0-9]+$ ]] && [ "$EXISTING_LIMIT" -ge 1048576 ]; then
  EXISTING_LIMIT_MIB=$((EXISTING_LIMIT / 1024 / 1024))
else
  EXISTING_LIMIT_MIB=1024
fi

TRAFFIC_GUARD_LIMIT_MIB="${TRAFFIC_GUARD_LIMIT_MIB:-$EXISTING_LIMIT_MIB}"
```

优先级：**显式环境变量 > 服务器已有配置 > 代码默认值**。

## 三个容易犯的错

### 错 1：先赋默认值，再尝试继承

```bash
SMTP_HOST="${SMTP_HOST:-smtp.gmail.com}"      # 这里已经有值了
SMTP_HOST="${SMTP_HOST:-$(read_existing SMTP_HOST)}"   # 永远不触发
```

变量非空后，`${VAR:-...}` 的默认分支再也不会执行。**所有可继承项必须先保持为空，继承完成后再补默认值。**

### 错 2：用 `${VAR:-0}` 又想区分“用户没说”和“用户说 0”

```bash
ENABLE_MAIL_NOTIFY="${ENABLE_MAIL_NOTIFY:-0}"       # 变成非空
if [ -n "$ENABLE_MAIL_NOTIFY" ]; then ... fi        # 判断失效
```

正确做法是先留一份“是否显式设置”的原始值：

```bash
MAIL_NOTIFY_EXPLICIT="${ENABLE_MAIL_NOTIFY:-${ENABLE_GMAIL_NOTIFY:-}}"
ENABLE_MAIL_NOTIFY="${MAIL_NOTIFY_EXPLICIT:-0}"
# 后面判断用 MAIL_NOTIFY_EXPLICIT
```

### 错 3：继承来的值不做校验

现场配置可能被手工改坏。继承后必须走一遍原有的正则校验，不合法的值回退到代码默认值，而不是直接写回。

## 排查手法

重部署后立刻 diff 配置：

```bash
# 部署前后各存一份
sudo cp /etc/default/traffic-guard /tmp/cfg.before
sudo bash scripts/install_linuxnet_stack.sh
sudo diff /tmp/cfg.before /etc/default/traffic-guard && echo "配置未变"
```

脚本里加日志，把最终生效值打出来，比事后猜快得多：

```bash
log "阈值 ${TRAFFIC_GUARD_LIMIT_MIB} MiB（来源：${SOURCE}）"
```

## 教训

- **“重跑一次”必须是验收项**。每次改安装脚本，都要在真机上不带环境变量重跑一遍，比对配置是否保持。
- 我第一版改动只继承了阈值，忘了邮件配置；第二版继承了邮件，又因为默认值遮蔽失效；第三版才全对。**这类 bug 只有真机重跑才能发现，静态检查完全查不出来。**
